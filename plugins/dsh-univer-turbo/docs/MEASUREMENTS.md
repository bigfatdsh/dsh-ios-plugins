## 二、本插件的效果（可复算）

`node tools/measure.mjs` 的输出：

```
原 14 个 univer 工具的模型可见定义合计  11,511 字符 ≈ 2,878 token（官方 /4）/ 3,198（实测 /3.6）
收窄后的门面                            2,804 字符 ≈   701 token（官方 /4）/   779（实测 /3.6）
每个请求净省                            8,707 字符 ≈ 2,177 token（官方 /4）/ 2,419（实测 /3.6）  降幅 75.6%
```

按实测平均请求长度 93,034 token 计，工具面占比从 **3.44% 降到 0.84%**。

其余机制的省量（按同一套账单口径推算）：

| 机制 | 依据 | 省量 |
|---|---|---|
| `batch` 合并往返 | 实测 25%~40% 的往返是重复调用；`compile_svg` 单页碎步 57/51 次 | 每省一次往返 ≈ 省一次 93,034 token 的整段上下文重发 |
| 只读记忆化 | 同上（重复调用直接归零） | 重复调用从「重跑 + 重发载荷」变成一行指针 |
| 截图预算 8 张/会话 | 实测两场分别投递 36 / 37 张图，携带 1.75M / 1.47M token | 图片携带成本降到约 1/4 |
| 渲染前分片 | 实测 `Image batch exceeds the configured image-count limit` 失败 3 次，每次烧 8 s + 一个往返 | 把「失败 + 重试」变成一次成功 |
| JSON 语义剪枝 | `univer_inspect` 无 range 时整单元转储；带 range 时每格返回**两遍**（`cellData` + `displayValues`） | 只对超预算的结果生效，实测这类结果是最大的单项文本结果 |

### v1.0.3 新增机制的量级（同一基准会话推算）

| 机制 | 依据 | 占会话 |
|---|---|---|
| 工具面收敛 | 11,511 → 3,130 字符，−72.8%，每次请求省 2,328 token | **2.6%** |
| 截图预算 8 张 | 36 张 → 8 张 | **12.1%** |
| 回声抑制 | 约 200 次 univer 结果 × 约 80 字符（路径 + operation 回声） | **~1.6%** |
| 按 op 预算 | `svg` 108 次 × 约 135 字符；`lint` 5 次 × 约 300 | **~1.7%** |
| 失败记忆化 | 3 次 `image-count limit` 失败 ×（8 秒 + 一个往返） | **~2.5% + 24 秒** |
| 分片并发渲染 | 3 片：串行 ≈18 秒 → 并发 ≈6 秒 | **~12 秒/次** |
| 往返次数削减 | 去重 + batch + one-shot 引导 | **0 ~ 40%（取决于模型配合）** |

**合计：保底 ≈ 20.5%，现实预期 25%~40%，上限 ≈ 55%。**

```
  ▸ [2] status (cached)  ...
  ▸ [3] status (cached)  ...
```

## 四、v1.0.8 的实测节省率与提速率

复算命令：`node tools/savings.mjs`（全部分会话输出）。数据源是 3 场真实会话的原始日志，
token 侧把 184 条真实结果真的过一遍压缩器并按携带成本加权；时间侧直接从
`tool/call → tool/result` 的时间戳量出每次调用的真实耗时。

### token 侧（只算机制确定能省的）

| 来源 | 计算 | 结果 |
|---|---|---|
| 工具面收敛 | (11,511 − 3,130) 字符 × 341 次请求 ÷ 3.6 | 793,867 token |
| 结果压缩 | 119,505 → 74,765 字符（−37.4%），按携带成本加权 | 546,831 token |
| **合计** | | **1,340,698 token = 4.26%** |

### 时间侧（只算能确凿消除的调用）

| 来源 | 次数 | 省下 |
|---|---|---|
| 重复编译被按页缓存挡掉 | 46 | 144.0 秒 |
| 重复失败被记忆化挡掉 | 1 | 8.3 秒 |
| 超限截图改走渲染前分片 | 3 | 23.8 秒 |
| **合计** | | **176.1 秒** |

- 占**工具耗时** 539.9 秒的 **32.6%**
- 占**会话墙钟** 3234.9 秒的 **5.4%**

### 分会话明细

| 会话 | 请求 | 省 token | 占比 | 省秒 | 墙钟 | 提速 | 重复编译 |
|---|---|---|---|---|---|---|---|
| 401e5895（PPT） | 128 | 577,206 | 5.1% | 89 | 692s | **12.9%** | 17 |
| 8c5eb015（同一任务重跑） | 90 | 409,774 | 4.9% | 87 | 662s | **13.2%** | 29 |
| f4453c36（插件安装会话） | 123 | 353,719 | 3.0% | 0 | 1881s | 0.0% | 0 |

**汇总的 4.26% / 5.4% 被第三场稀释了**——那是一场 1881 秒的插件安装会话，几乎没有 univer 工作
（但它仍然按请求数支付了工具面的省量）。**两场真实 PPT 任务的数字是：token −5%，墙钟 −13%。**

### 为什么墙钟只降 13%，而不是 94%

日志显示**渲染类工具占工具耗时的 94%**（`compile_svg` + `screenshot` + `lint` + `print_pdf`）。
本插件能消除的是**重复的**那部分调用；单次调用的固定代价——每次 spawn 一个 31.6 MB 的
Node worker（实测冷启 0.57 秒）+ 每次渲染重启一个 Chromium——**写在 `univer-office` 的
`finally` 里、无池化，仅在插件层无法触及**。

墙钟的其余部分是模型推理（实测平均 2.76 秒/往返）与人工等待；本插件不改变往返次数，
因此那部分动不了。

### 未计入的部分（诚实标注）

- **batch 合并往返 / one-shot 引导**：潜在最大，但完全取决于模型是否照做，无法保证
- **截图预算**：日志里 73 张图，按每会话 8 张计会扣下 56 张；但模型 `force:true` 即归零
- **只读记忆化**：省的是网关调用与延迟，token 侧只体现为一行指针
