# 设计取舍

这份文档记录**为什么是这样，而不是那样**。每一条都对应一个被量出来的事实。

## 1. 为什么是「收窄工具面」而不是「缩减描述」

原 14 个工具的描述只占 2,192 字符，参数 schema 占 8,994 字符。单纯改描述最多省 20%，
而收敛成门面能省 75.6%——因为省掉的是**每个 op 都要重复一遍的 `file` / `unitId` /
`worktreeId` / `output` 的类型声明与校验结构**。

## 2. 为什么门面用扁平参数，而不是 `{op, args:{}}`

`{op, args}` 看似更省 schema，实际更贵：模型必须凭记忆写 `args` 的键名，
写错一次就是一次完整往返（实测平均 93,034 token）。把 29 个参数名平铺出来只花约 1,200 字符，
而**避免一次往返就赚回约 30 次请求的这笔开销**。描述里的参数速查行同理保留。

## 3. 为什么描述改成英文

同一份信息，中文约 1 token/字符，英文约 0.25 token/字符。这段文字每个请求付一次，
改成英文把 979 字符压成约 350 token 等值——**纯赚**。

## 4. 为什么门面能安全转发给「已经隐藏」的工具

`ctx.tools.get(name)` 省略 scope 时走的是**全局视角**，不受任何 agent 作用域上的
restrict 掩码影响；`restrict` 只是过滤「这个作用域继承到什么」，从不删除注册。
所以门面拿到的是**同一个**经过作者校验的执行体，而不是复制品：
参数校验、错误类型、超时语义全部保持原样。这一点由真实 ToolRuntime 的集成测试守着。

## 5. 为什么压缩必须先 JSON 语义、后文本预算

通用截断器（本 profile 已装 `dsh-tool-token-optimizer`）的强项是日志类文本。
但 Univer 的结果是结构化 JSON：截断会立刻产生两个恶果——JSON 不再合法（模型无法局部引用，
只能重跑），尾部的结论字段（`ok` / `error` / `total`）被切掉。
所以顺序是先语义剪枝（删空值、限数组、限长字符串、限深度，逐级加严），
剪完仍超预算才退回文本预算。

## 6. 为什么报错子树整棵免剪

路径上出现 `error/issue/warning/fail/stack/reason/violation` 就跳过整棵子树。
报错信息是模型自我纠错的**唯一**依据；为了省几百 token 让模型看不到失败原因，
代价是整轮返工。

## 7. 为什么省略说明必须三要素齐全

「丢了多少 / 里面有多少条报错行 / 怎么拿回来」——三者缺一，模型就会重跑工具，
省下的 token 连本带利还回去。这不是措辞问题，是数学问题。

## 8. 为什么记忆化命中时「只回指针」是安全的

因为上一次的完整结果**仍然在对话历史里**。指针不丢任何信息，只是不让同一段内容
在上下文里出现两次。载荷较小时（< `memoPayloadChars`）仍然重发，
避免模型为了一个 200 字符的结果回头翻。

## 9. 为什么「执行中」的调用也算缓存命中

这是活验证里抓到的真实缺陷：`batch` 内两个完全相同的只读步骤是**并发启动**的，
若只认已完成的缓存，第二个会错过并再打一次网关。修法是把 in-flight 的 Promise 也登记进表，
并且**必须在写入缓存之后**才放行等待者——否则它会醒来发现缓存仍是空的。

## 10. 为什么绝不改写历史

前缀缓存占全部 token 的 98.3%。任何对已发出消息的改写，都会让从改动点往后的整段前缀作废。
所以工具表只在 `agent/created`（会话第一个请求之前）动一次，之后永不增删；
所有压缩都发生在 `tools/post-execute`——结果还没进过任何请求的那一刻。

## 11. 为什么不重编码图片

降采样需要 PNG 解码 + 重编码，代码量与出错面都很大，而收益可以用更便宜的方式拿到：
预算、去重、渲染前分片，以及（可选的）默认 scale。
把复杂度花在「少截几张」上，比花在「把图压小」上划算得多。

## 12. 为什么默认不打开 `defaultScreenshotScale`

图片 token 随 scale² 下降，但保真度不够会让模型重截一次——一次重截的成本
高于十次省下的图片 token。所以把它做成显式开关，默认不干预宿主的 `scale: 1`。

## 13. 为什么装配阶段永不抛错

插件的全部价值是「让调用更便宜」。它没有资格因为任何环境差异
（context 形状、字段只读、服务缺失、版本漂移）让宿主多出一行 failed 的插件，
更没有资格影响工具调用本身。所有失败路径都只记一条 warn 并降级。

## 14. 为什么「回声抑制」不违反「不许改写信息」

它删的是结果里**只是把调用参数念一遍**的字段（`file` / `unitId` / `worktreeId` /
`output` / `source`）与完全由 op 决定的 `operation`。信息并没有消失——它在**紧邻的调用参数**里。
这与「指针式记忆化」依赖的是同一个前提：调用与结果成对出现在同一段上下文中。
所以有两条纪律：**不是回声就不删**（路径不同源 = 新信息），以及**随时可以用
`stripEcho: false` 关掉**。

## 15. 为什么预算要按 op 走，而不是调小全局预算

全局调小会误伤 `inspect`（真的可能很大，且截断它会丢结构）；
全局保持 1400 又放过了 `compile_svg`（108 次调用、均值 615 字符、每次都带路径与 viewport 回声）。
按 op 收紧是**精确**的做法：只压那些「已知又小又啰嗦」的结果。

## 16. 为什么确定性失败可以记，超时不可以

实测里 `Image batch exceeds the configured image-count limit` 连撞 3 次，
每次 8 秒 + 一个完整往返。这类失败的**结果只取决于入参和文档状态**，
两者都没变时重跑必然得到同样的结果——记下来是纯赚。

超时/中断/连接抖动不同：它们可能是瞬时的，记下来等于剥夺模型重试的机会。
所以只记确定性失败，并且**报错永远全文重发**（不能让它去上文里翻），
而且任何一次成功的写都会让整张表失效。

## 17. 为什么截图分片要并发，而写操作仍然串行

每次渲染都是一次独立的浏览器启动（实测单次约 6 秒），所以分片并发是**线性**的收益：
3 片从 18 秒降到 6 秒。分片之间互不影响（不同页、只读渲染），并发是安全的。

但 `compile_svg` 这类**写**操作不同：它们各自基于当前 revision 生成新 revision，
并发跑同一 unit 的不同页有冲突风险。实测显示 `compile_svg` 占了 176 秒 / 347 秒的工具耗时，
并发化的诱惑很大——但**一个被写坏的文档比慢 3 倍严重得多**。
所以这里刻意不做，并把理由写在这里，而不是留一个默认打开的隐藏开关。

## 18. 为什么并发合并必须保序

并发不允许改变输出字节。合并时严格按原分片顺序拼接，
因为前缀缓存要求「同一前缀逐字节相同」——一旦顺序随调度变化，
每次重放都会作废缓存，省下的等待时间会以数十倍的 token 重新计价还回去。
